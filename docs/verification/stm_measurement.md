## 1. STM のデータ構造 (service_id 命名から読める運用)

`25M-H56M000A-82-A` = [年+シーズン]-[営業所+版]-[改定番号]。実測で確認した構造:

1. **シーズン**: 25M (2025 春 3〜6月) / 25U (été 夏 6〜8月) / 26J (janvier 冬 1〜3月)
   / 26M (2026 春)。全ラベル (平日・土曜・日祝・月曜・金曜) がシーズンで
   2世界に割れる — これ自体は SD5 の意図どおり。
2. **営業所 (garage) 分割**: 同一シーズン内は GLOBAUX (全域) + H50〜H62
   (営業所毎) の10〜18 service が**同一日付集合** (equal) で並走。
   土曜1日に全 service 合計 ~1,300〜2,200便。
3. **傘 service**: GLOBAUX はシーズン全期間 (12日)、営業所 service が
   期間内で差し替わっても全体を覆う (nested)。
4. **シーズン内差し替え**: 26M 土曜 = 前半 `-70-` 版 (3/28〜5/16、8日) +
   後半 `-80-` 版 (5/23〜6/13、4日)。**日付は互いに素** (disjoint 64組)。
   利用者認識では「5/17 改定の前後」= 2つのダイヤ。
5. **特異日の全面差し替え**: 26J 土曜に `JV00A` 版が 3/7 のみ (全営業所同時)。
   base (3/7 を含む10日) と部分重なり (partial 8組)。
6. **シーズン初日の旧版残り**: 25M 土曜で `-80-` 版が 3/29 のみ残り
   `-82-` 版が 4/5 以降 — **立川の 2/28 削除漏れと同型**のデータ運用。

## 3. 診断 — 独立した3つの問題

**(i) 世界の融合規則が STM の構造単位を潰す (主因)。**
「1日でも日付を共有すれば融合」(連結成分) は、
- 傘 (GLOBAUX 全期間) が前半版と後半版を**橋渡し**して1世界に融合させ
  (前半・後半は互いに素なのに)、
- 特異日 V 版 (1日) が base と融合して mixed にする。
結果、利用者認識の単位 (「5/17 改定の前後」「3/7 だけ特別」) が
1つの「のべ」世界に潰れ、便数の意味が失われる。日付集合の対関係の実測では
**equal (営業所並走) + nested (傘) + disjoint (差し替え) がほぼ全部**で、
本質的に曖昧な partial は特異日 V 版の8組のみ。つまり STM のデータは
構造的に分解可能なのに、連結成分がそれを見ていない。

**(ii) v1 便対応が世界セルを知らない。**
便対応は (family×方向×ラベル) 粒度で組むため、対の 37% がセルを跨ぐ
(旧春の便 ↔ 新の別シーズンの便など)。④時刻表の列はこの対から作るので、
ヘッダ (セルの全便) と④ (対の自セル側) が構造的に一致しない —
self_check 900件の直接原因。国内フィードで顕在化しないのは
セルが少なく跨ぐ相手がないため。

**(iii) ペア自体が期間非重なり (10か月離れた2時点)。**
I1 で取得した2世代は 2025-03〜08 と 2026-01〜06 で共通日付がない。
dates 信号は原理的に不発 (実測 0件)、旧夏シーズンは相手がなく
old_only = 廃止の見かけ。STM は GTFS を頻繁に更新するので、
Mobility Database のアーカイブから**期間の重なる隣接版**を取れば、
比較条件そのものが変わる (SD6 の単調交代判定が効く可能性もある)。

## 4. 設計の選択肢 (次の判断材料 — 実装は未着手)

- **案X: 世界の分解規則を「連結成分」から「日付集合の同値類+包含」へ。**
  同じ日付集合 (equal) は同一世界、包含 (nested) は共走 (合算正当、現行の
  入れ子除外と同じ扱い)、互いに素は別世界。partial のみ現行どおり保守的に
  (mixed か特異日切り出し)。→ STM は「前半ダイヤ/後半ダイヤ/特異日 3/7」に
  自然に分解され、のべが消え、1日あたり便数が正確になる。
  立川 (2/28 型) は「特定日① 12/30 (+2/28)・特定日② 12/31 (+2/28)」の
  2世界になり、共有日が両タブに現れる形 — 案Cの「のべ+⚠」より
  情報は増えるが、「同じ日が2タブに出る」ことの是非は要判断。
  データの主張に忠実という原則は保てる (日付集合はデータそのもの)。
- **案Y: ④の表示ペアリングをセル内に制約する** (双子写像の拡張)。
  (ii) への対処。案Xで世界が正しく割れても、v1 対応の跨ぎは残るので
  いずれ必要。セル決定後にセル内で再ペアリングする2パス構成。
- **案Z: STM の隣接版ペアで再評価** (データ側の対処)。(iii) への対処。
  案X/Y の効果測定にも、期間の重なるペアの方が本来の利用シナリオに近い。

推奨順: 案Z (データ取得、安価) で条件を正してから案Xの設計判断 → 案Y。
案Xは day_worlds のコア変更 (SD5 の再訪) なので、国内検証フィード全部での
退化保証 (equal/nested のみのフィードは現行と同一分解) を DoD にする。
