# UI レイヤーの整合性監査と品質維持の仕組み (2026-07-26)

背景: SD5/SD5b/SD5c/SD6 (service_id 精緻化) の際、コアはほぼ正しく動いたのに
UI の不整合 ([object Object]、桑名の平日分裂、しんぐうの日付固着、立川ののべ表記漏れ)
が続発した。ユーザーの問題提起は2点:

1. UI レイヤーは古い構造のまま、指摘への点対応 (パッチ) を重ねただけではないか。
   本来 service_id 精緻化に連動した UI 側の面的改修が必要だったのではないか。
2. UI はレンダリングが絡みテストしにくく、チェックが疎かになる構造がある。
   整合性・一貫性を指針化して評価する仕組みが必要ではないか。

監査の結論: **疑いは正しい。** SD5 の「表示は世界セル・便数は1日あたり・
のべは断定しない・日付ランは年境のみ分割」という新しい表示規約は、
指摘を受けた表示経路にしか適用されておらず、同じ概念を表示する他の経路が
旧規約のまま残っている。以下に全件を列挙する。

## 1. 監査で見つかった不整合 (2026-07-26 時点)

### 重大 (ユーザーに見える嘘・矛盾)

- **A1. 第1部「曜日区分ごとの便数」が世界を知らない生カウント**
  (bundle.py `_feed_overview` の day_counts)。trip を素の day_type で数えるため、
  PRT 型 (同内容の双子世界) では第1部が「特定日 38→76 ▲+38」、第3部が
  「特定日 38→38」と**同じレポート内で矛盾する数字**を出す。SD5 の
  「便数=1日あたり (代表世界)」は第3部にしか適用されていない。
- **A2. 路線ページ折りたたみヘッダ `dayCount()` が mixed を知らない**
  (RoutePage.svelte)。立川は展開すると「のべ28便」だが、折りたたみ行は
  「特定日① 28→16便▼」のまま。SD5c の修正は `tabLabel()` だけだった。
- **A3. 一言ダイジェスト `_digest()` も mixed を除外しない**
  (presentation.py)。`day_totals` の old≠new をそのまま「特定日①12便減」と
  文章化し得る (A2 と同根)。
- **A4. SD3 special_dates 経路に「cap 後圧縮」バグが残存**
  (bundle.py で 30 日に cap → viewer `formatDateRuns` で圧縮)。
  しんぐうで直したのは SD5b cellMeta 経路 (サーバー側全日付圧縮) だけ。
  **1世界の特定日ページ** (cellMeta が付かない側) で運行日が 30 日を超えると、
  今も「3/1〜3/30 ほか215 (計245日)」型の誤誘導表示になる。
- **A5. 日付ラン圧縮の実装が3つ・規則が2種類**。
  - `presentation.date_runs_year_split` (Python、年境分割) — cellMeta 用
  - `bundle._date_runs` (Python、**年境分割なし**) — SD4 運行日の要点
    (「曜日と異なるダイヤで走る日」「運行のない日」「内容が異なる期間」) 用
  - `i18n.formatDateRuns` (JS、年境分割) — special_dates 用
  ユーザー指定「日を列挙するときは年境 (12/31|1/1) のみ分割」は SD4 note には
  適用されておらず、第1部では 12/30〜1/3 が繋がって出る。

### 中 (潜在バグ・導線欠落)

- **B1. `sameSpecial` が cap 済みリスト同士の比較** (RoutePage.svelte)。
  total を見ないため、先頭 30 日が同一で総日数が異なる場合に
  「新旧同一」と誤って1行に畳む。
- **B2. presentation 整合チェック (ヘッダ便数 vs ④列数) が logger.warning のみ**。
  レポートにも検証モードにも出ないため、STM 級の食い違いが「サーバーログに
  warning 多数」のまま可視化されず放置される。網羅性を accounting で
  構造保証している検出側と対照的に、**表示側の台帳は誰も見ない場所に流れる**。
- **B3. 語彙の橋渡しなし**: 第1部の特定日内訳は service_id 生表示、
  第3部は ①② (世界)。同じものを指す2つの名前に相互参照がない。

### 構造 (ドリフトを生む機構そのもの)

- **C1. 「旧→新▲▼」便数表記が4箇所で独立実装**
  (`tabLabel` / `dayCount` / `tbCount` / FeedOverview `delta`)。
  mixed のような属性追加が1箇所にしか入らない事故は、この構造の必然。
  日付ランの M/D 整形も cellDates / formatDateRuns / runsText の3箇所。
- **C2. バンドルに schema_version がない**。互換分岐は「runs_old があるか」等の
  フィールド嗅ぎ分け。RD1b の分離配信 + lazy 再生成で app と data の版ずれが
  常態化する設計なのに、契約が暗黙。
- **C3. viewer にテストが1件もない** (package.json に test script なし)。
  pytest 237 件は全部 Python 側。`formatDateRuns` の年境分割のような「仕様」が
  JS 側に入ってもテストされず、しんぐうのリアクティビティバグ (タブ切替で
  再描画されない) を捕まえる層が存在しない。
- **C4. presentation.md は R1〜R19 の要件凍結・改訂履歴の運用が機能している**が、
  記述の単位が「どの部に何を出すか」であり、**横断規則 (どこに出ても守るべき
  表示不変条件)** を持たない。SD5 が導入したのはまさに横断規則
  (便数の意味・のべ・年境分割) だったので、部単位の要件改訂では波及先を
  拾いきれなかった。

## 2. 原因の整理

- コアは「説明台帳」という構造的な網羅性保証を持つが、表示層には対応物がない。
  同じ事実 (便数・日付・mixed) を複数の表示面 (第1部/タブ/折りたたみ/ダイジェスト/
  SD4 note) がそれぞれ独立に整形しており、**規約変更の波及先一覧が存在しない**。
- テストの非対称: 検出はルール毎に合成テスト必須 (開発ルール) だが、
  表示には同種の Definition of Done がない。「検証フィードで目視」が唯一の網で、
  目視はユーザーの指摘とほぼ等価 = 指摘駆動の点対応になる。

## 3. 仕組みの提案

### S1. 表示規約 (presentation invariants) の明文化 — presentation.md に PI 節を追加

部単位の R 要件とは別に、横断不変条件を番号付きで凍結する。初版:

- **PI-1 便数の意味**: レポートモードに出る便数はすべて「表示便数」
  (代表世界のみ・1日あたり)。生カウント (のべ) を出すときは必ず「のべ」を冠する。
  第1部・第3部・折りたたみ・ダイジェストで同一の数字が出ること。
- **PI-2 mixed の伝播**: mixed な世界を含む数字は、それが現れる**すべての**面
  (タブ・折りたたみ・ダイジェスト・第1部) で のべ表記+⚠注記の対象になる。
- **PI-3 日付ラン**: 日付列挙は常にサーバー側で全日付からラン圧縮し、
  連続日は月を跨いで繋げ、年境 (12/31|1/1) のみ分割する。cap 後の圧縮は禁止。
  実装は `date_runs_year_split` の1本のみ (`_date_runs` は廃止)。
- **PI-4 記号第1チャネル** (既存原則の再掲): ▲▼・のべ・⚠ が第1チャネル、色は補強。
- **PI-5 語彙の同一性**: 同じ対象 (世界・セル) は全部で同じ表示名 (①②) を使う。

以後「表示規約を変えたら PI を同期更新し、波及先を PI 単位で棚卸しする」を
開発ルールに追加する (detection.md 同期ルールの表示版)。

### S2. 整形関数の一元化 (ドリフトの機構的封じ)

- viewer: `lib/format.js` に `fmtTripCount(old, new, {mixedOld, mixedNew})` /
  `fmtRuns(runs, more, total, lang)` を置き、RoutePage / FeedOverview /
  BandMatrix の該当箇所を全部これに寄せる。
- Python: ラン圧縮は `date_runs_year_split` に一本化。
- バンドルに `schema_version` (整数) を追加。viewer は対応範囲を宣言し、
  互換分岐はフィールド嗅ぎ分けでなく版番号で行う。

### S3. 表示のセルフチェックを「台帳」に昇格

- presentation 整合チェック (ヘッダ vs ④列数、今後 PI-1 の部間一致も) の違反を
  `presentation["self_check"]` に構造化して格納し、
  検証モードに「表示整合セルフチェック」パネルとして表示する
  (explained_ratio と同格の扱い)。
- 回帰スクリプトは self_check 非空を fail にする。目視の前に機械が拾う。

### S4. viewer テストの導入 (vitest)

- **純関数テスト**: `formatDateRuns` (年境分割・cap)・`dayName` (@N/dow_)・
  S2 で作る整形関数。ロジックの大半はここに寄るので費用対効果が最大。
- **コンポーネントテスト** (@testing-library/svelte): RoutePage に固定 page を
  与え「タブ切替で日付文字列が変わる」「mixed タブで のべ が出る」を assert。
  しんぐうのリアクティビティバグはこの1本で捕まえられた。
- **表示射影スナップショット**: 検証フィードの bundle から、ユーザーが読む
  文字列 (タブラベル・折りたたみ行・cellMeta 行・第1部の便数表) だけを
  抽出する小さな射影を書き、スナップショットとして固定。ブラウザ不要で
  「サーバー変更が表示文字列をどう変えたか」の diff が CI で見える。
- `scripts/build_viewer.sh` に `npm test` を組み込み、テストが落ちたら
  テンプレート同梱を止める。

### S5. DoD の対称化 (開発ルール追記)

検出ルールの3点セット (ドキュメント・合成テスト・実フィード目視) に対応する
表示変更の3点セットを定める:
**PI 棚卸し (波及先一覧) ・ vitest (純関数 or 射影) ・ 検証フィードでの目視**。

## 4. 適用順 (提案)

1. 不整合の修正バッチ (A1〜A5, B1): S2 の整形一元化と同時に行うのが最小工数
   (バラバラに直すと4箇所実装がまた増える)。
2. S1 (PI 節) と S5 (DoD) の文書化。
3. S3 (self_check) + S4 (vitest 最小セット: 純関数+RoutePage 1本+射影)。
4. B3 (語彙の橋渡し) は独立の表示改善として別判断。
