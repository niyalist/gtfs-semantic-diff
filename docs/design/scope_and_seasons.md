## 1. 問題の設定 — STM が突きつけたもの

STM (モントリオール) の GTFS は「長期をカバーするファイルの中に、最初から
複数シーズン (数ヶ月で切り替わる時刻表世代) が同居し、その構造が毎年繰り返す」
という作りである。営業所別 service の並走、シーズン全期間をカバーする通年
service、シーズン内改定版、特異日の全面差し替え版が重なる (類型H、
service_id 類型学 docs/articles/service_id_typology.md)。スイス統合フィードも
同型。この構造に対して「本ツールは何を目指すのか」が本書の主題。

## 2. 前提の確認 — 融合原則の非対称性 (2026-07-29 ユーザー明確化)

指示は「**1日も共有していないものを融合させるのはおかしい**」であり、そこから
「1日でも共有すれば融合」は**導かれない**。現行実装 (連結成分) は許される
設計空間の中の最も粗い選択にすぎない。したがって論点は「原則を緩めるか」では
なく「**共有がある集合たちを、どの基準で束ねるのが読者にとって正しいか**」
という自由度の中の設計判断である。案X (日付集合の同値類 equal + 包含 nested +
排他 disjoint の直接判定) はその空間内のより細かい選択。

## 3. 検出可能性 — シーズン構造は意味付けなしで見抜ける

機械的シグナルは3つ。いずれも観察であり「これは夏ダイヤ」という意味付けを
要しない:

1. **連鎖**: 同一ラベル内の世界群が互いに素な期間のチェーンとしてフィード窓を
   ほぼ埋める → 期間分割構造
2. **通年層**: チェーン全体をカバーする service の併走 (STM GLOBAUX) →
   包含として検出
3. **反復**: 1ファイルでは原理的に見えないが、**比較ペアの両側に同型の連鎖が
   あること自体が反復の証拠**。年次反復の本格的扱いは多世代タイムライン
   (roadmap 将来項目) の領分

**通年層の扱い**: 日本のフィードで確立済みの「入れ子共走 (平日フル+学期のみ)
は合算が正当 (mixed にしない)」と同型に扱える。利用者がシーズン k に体験する
のは「通年便+シーズン k 便」なので、**運行の記述としては各シーズンへの合算、
構造の記述としては『全期間共通』の一度きりの注記**、で両立する。

## 4. 二つの比較意味論 — どちらも正しい

- **同一シーズン比較** (去年の夏 ↔ 今年の夏): 「平日は平日と比べる」の期間軸
  への延長。ネットワークの年次変化を答える
- **隣接シーズン比較** (夏 → 秋): 利用者の「昨日までと今日からの違い」。
  形は SD6 (世代同梱の切替) と同一で、**STM ではファイル内のシーズン境界こそ
  が改正**である。本ツールの本業が「改正の説明」なら、STM は**1ファイルだけ
  でもレポートが書ける**対象 (単一 GTFS 入力の改正レポートという製品拡張)

どちらかを正解にしない。同じ構造の上の**別のクエリ**であり、正解選択ではなく
クエリの指定可能化が答え。

## 5. ワンクッション案 (ユーザー提案) — スコープの明示化

「GTFS に意味のある分割 (シーズン・agency) があるかを検出し、ある場合に
何と何を比べるかを問い合わせる1ステップを挟む」。検討の結論として有望:

1. **意味論のジレンマの誠実な解消**: どちらの比較を出すかを機械が推測するのは
   避けてきた「意味付け」。検出した分割を証拠付きで提示し (期間①: 3/24〜6/13・
   service 11本、…)、選択は人が行う — 「機械が断定するのは観察のみ」と整合
2. **既存概念の一般化**: SD6 の comparison_scope (自動検出スコープ) を
   **ユーザー指定可能なパラメータ**に昇格させるだけ。コアは「スナップショット
   2つ+スコープ → イベント」の純関数のまま。決定性・JSON 契約は不変。
   Web ではジョブパラメータ = URL・版管理の単位に自然に乗る
3. **agency 指定は独立に筋が良い**: agency_id は GTFS が明示宣言する分割で
   推測不要。国家統合フィード (swiss/OVapi) で計算コストと可読性が桁で改善。
   シーズンと独立に先行実装できる

設計上の固定点 (先送り後も変えない前提):

- **既定値は現行動作 (全体比較)**。CLI バッチ・lazy 再生成は対話できない。
  ワンクッションは「検出したら第1部に構造を注記し、UI に『シーズン別に
  比較し直す』導線を出す」形 — 入力によって比較の既定が変わると予測可能性を
  失う
- **案X とワンクッションは代替でなく合成**: 案X = 構造を正しく検出する層、
  ワンクッション = その構造のどの単位を比べるかを人に問う層。route 46 の
  「のべ116」も、構造検出が直れば「冬58+特異日差替58」として提示できる

## 6. 段階案 (再開時の候補、roadmap §SC)

1. **SC1 agency 指定** — 低リスク・独立・国際化 (I) の実利。入力 UI と
   スコープパラメータの最初の実装例
2. **SC2 世界分解の精密化 (案X)** — 連結成分 → 同値類+包含+排他。
   コア (day_worlds) の再訪。DoD: 「共有なし→融合しない」堅持、国内全検証
   フィードの退化保証 (equal/nested のみのフィードは現行と同一分解)、
   STM group 46 残余 (self_check 2件) の解消、mixed 231ページの実質削減。
   検証装置は京都対応で整備済み (presentation ハッシュ照合・self_check・
   保存則三面一致)
3. **SC3 シーズンのスコープ UI + 期間非重なりの言い分け** — 検出結果の提示、
   同一シーズン対の推奨、「廃止」と「比較対象期間なし」の区別表示 (案Z の
   隣接版データ取得での再評価を含む)
