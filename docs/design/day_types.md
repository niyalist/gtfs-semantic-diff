# day_type の語彙の精密化 (M10) — 「特定日」の解体

状態: **承認・実装 (2026-07-09)**。検証ログ: docs/verification/M10_day_types.md。
後続検討: **docs/design/service_days.md** (2026-07-23 — 実効運行日集合による
精緻化。PRT の祝日専用 service 誤分類 IN-8 と日本の世代同梱型を受けて)。
背景: ユーザーの問題提起「特定日という表示はどういう含意か。パッと全体を掴む
目的に対して分かりにくい」+ 日付↔service が 1:N である (同じ日に複数 service
が有効になりうる。平日ベース+月水だけ増便、のような GTFS が組める) との指摘。

## 1. 実態調査 (2026-07-09、キャッシュ43フィード)

「特定日 (irregular)」に分類される service の悉皆調査:

| 型 | service数 | 便数 | 実例 |
|---|---|---|---|
| **曜日指定運行** (calendar フラグが6分類外) | 65 | 1,099 (83%) | 朝日町「月・火・水・金」「木」、上松町「水曜(通学利用)」、安芸市「火木」、明知鉄道「月以外の毎日」 |
| **短期 calendar_dates** (≤10日) | 16 | 219 | 永井「年末・年始」(5日で111便のフルダイヤ)、「土日祝臨」、花巻「第1・4土曜」 |
| **運行日ゼロ** (全フラグ0・日付なし) | 名古屋4件 | 24 | 「平日深夜」「終車延長」— 休止中の定義枠 |
| 日数多数・曜日多数決落ち | **0** | 0 | (観測されず) |

さらに曜日指定 service と他 service の**関係** (曜日集合の包含):

- **増便/限定型** (より広い service に包含): 53/72 — 平日ベース + 月水の通学便など
- **単独型**: 19/72 — 有田川町「水曜日(金屋)」など地区別曜日運行のコミュバス
- **置き換え型** (短期 calendar_dates): 永井 年末年始 = 平日・土日祝が
  exception_type=2 で当該5日を運休し、専用ダイヤが走る (追加ではなく代替)

結論: 「特定日」の中身は大半が**完全に規則的な曜日指定運行**であり、
「特定日」という語は実態と逆。また day_type は週の分割ではなく**重なり**を持つ
(増便型が多数派) ので、その関係を示さないと誤読される。

## 2. 設計

### 2.1 day_type の語彙 (決定的・世代間安定)

| 値 | 判定 | 表示 (ja) |
|---|---|---|
| weekday / saturday / sunday_holiday / weekend / daily | 従来どおり | 平日 / 土曜 / 日祝 / 土日 / 毎日 |
| **`dow_XXXXXXX`** (X∈{0,1}、月→日の7ビット) | calendar フラグが上記5型のどれでもない | ビットから生成「月・水曜」等 |
| irregular | calendar_dates のみで日数 ≤ short_service_max_days、または曜日多数決 < majority | 特定日 |
| **`inactive`** | 全フラグ0かつ追加運行日なし | 運行日なし |

- 曜日フラグ由来なので `dow_*` は世代間で安定 (同じ運用なら同じ値)。
  trip 照合のブロック (group × day_type) も自動的に精密化される
  (従来は月火水金ダイヤと木曜ダイヤが同じ「特定日」プールで照合されていた)。
- 日付ベースだが規則的なもの (第1・4土曜など) は解釈しない —
  irregular のまま日付要約を見せる (過剰適応の回避)。

### 2.2 関係の注記 (プレゼンテーション層、決定的)

1. **増便/限定型**: 路線ページ内で、`dow_*` の曜日集合を包含する day_type の便が
   同居する場合、曜日タブ・集計に「(平日に追加)」を付す。包含が複数あれば
   最小の上位集合 (同点は R16 順)。閾値なし (集合包含と便の有無のみ)。
2. **置き換え型**: 特定日 (irregular) / 運行日なし (inactive) の service は
   第1部 (フィード全体) に内訳を出す: service 名・日数・期間・便数と、
   「その全日付を他 service が exception_type=2 で運休しているか」
   (真なら「期間中は通常ダイヤ運休」= 置き換え、偽なら「通常ダイヤに追加」)。
3. R16 の曜日固定順は 平日→土曜→日祝→土日→毎日→**曜日指定 (dow)**→特定日→
   **運行日なし** に拡張 (dow 同士はビット列で決定的に整列)。

### 2.3 やらないこと

- 日単位の厳密展開 (ある日の全便合成)。「パッと掴む」層は day_type 抽象 +
  関係注記が担い、厳密な差分は説明台帳が保証する、という役割分担を維持
- 祝日カレンダーの参照 (既定方針の維持、detection.md §0)
- day_type 跨ぎの trip 照合 (平日→月水 への便付け替えは減便+増便に見える)。
  包含関係にある day_type のブロック統合は自然な拡張だが、実害の観測を
  待ってから (M8 以来の既知の制限として明記)

## 4. 追補 (2026-07-26 調査・提案・未実装): calendar_dates 専用 service の dow 検出

### 4.1 発端 — 根室交通 落石線の「平日①〜④」

https://diff.gtfs.jp/r/nemurokotsu__nemurobus__b830a268__31577a0e.html で
平日タブが4分裂 (①1便 ②1便 ③2便 ④1→0便▼)。実データ調査の結果:

- 根室は calendar に 平日/土日祝 の2行のみ。**「特別ダイヤ１」(毎週水曜の
  差し替えダイヤ) は calendar_dates の列挙のみ**で定義され (水曜を平日から
  type=2 削除し特別ダイヤ１を type=1 追加)、trips 3便を持つ。
- `_classify_dates` (calendar_dates 専用 service の分類) は**平日/土/日の
  3ビン多数決しかなく dow_XXXXXXX を出せない**。水曜100%でも「weekday」になる。
- 結果、平日ラベルに {平日} と {特別ダイヤ１} の2世界 (日付は互いに素) が同居し、
  世代間セル対応で4セルに割れた。**M10 が calendar フラグに対して行った
  「曜日指定の一級化」が、calendar_dates 表現には未適用**だったのが根本原因。
  同じ「毎週水曜運行」でも、フラグで書けば「水曜」、日付列挙で書けば「平日」
  になる — 表現の違いがラベルの違いになっていた。

なお根室のデータは「水曜差し替えの列挙が 9/24 まで (公開から約半年分) しかなく、
それ以降の平日は水曜を含む」— **ダイヤデータは直近が高精度で未来の尾部は
未整備**という実態の好例 (この非対称性は別項 4.5)。

### 4.2 提案規則

`_classify_dates` に、short ガードの後・3ビン多数決の前に dow 検出を挿入する:

1. 運行日数 ≤ short_service_max_days → 特定日 (現行どおり、変更なし)
2. **dow 検出**: span 内の各曜日の出現率 cov[dow] = 運行日数/spanのその曜日数。
   cov ≥ dow_on の曜日を活性とし、活性曜日外の日の比率が dow_stray_max 以下
   なら、活性曜日集合を `_classify_day_flags` と同じ写像でラベル化
   (全平日→weekday、土日→weekend、全曜日→daily、その他→dow_XXXXXXX)
3. 検出不能 → 3ビン多数決 (現行どおり、変更なし)

閾値は config [load.day_types] に dow_on (試作 0.6)・dow_stray_max (試作 0.1)。
フラグ持ち service は対象外 (フラグが明示的な曜日意味論)。

### 4.4 論点 (実装前の判断事項)

1. **irregular→daily の妥当性**: 「期間限定だが期間内は毎日」を「毎日」タブに
   するか。世界の日付注記が期間を示すので daily 化が読みやすい一方、
   kumanogobobus (cov 0.75) のような歯抜け毎日も daily になる。dow_on を
   上げる (0.7) 選択肢あり。
2. **added_to 注記**: dow_0010000 ⊂ weekday の同世代共存で「(平日に追加)」が
   付くが、根室は追加でなく**置き換え** (平日から水曜を削除)。削除日との
   照合で「(水曜は平日ダイヤを置き換え)」に出し分ける拡張は M10 の
   replaces_regular と同型 (任意、初版では保留可)。
3. 土日祝+祝日の cd 列挙は stray (祝日分) が閾値を超え検出不能 → 3ビンで
   weekend/sunday_holiday (現行どおり)。祝日認識はしない方針を維持。
4. 実装時の同期更新: detection.md §0/§2.4、本書 §3、検証5フィードの回帰
   (永井は cd 専用7 service を持つがラベル変更なしを実測済み)。

### 4.5 併せて記録する一般原則 (2026-07-26 ユーザー方針)

- **融合原則の明確化**: 「1日も共有しないダイヤは融合しない」は堅持。
  ただし「共有があれば必ず融合」までは求めていない — 共有時の融合粒度は
  設計余地 (STM の傘/差し替え問題 = stm_measurement.md 案X はこの余地の中)。
- **精度の時間非対称**: ダイヤデータは直近が高精度・未来の尾部は低精度
  (改訂版が出る前提の暫定)。有効期間の**開始のばらつきは真剣に扱い、
  終了のばらつきは軽く扱ってよい**場合がある。根室の水曜列挙 (半年分のみ) が
  実例。将来の適用候補: 世界の終端日差を分割根拠として弱く扱う、
  データ終端付近の差分の注記。
