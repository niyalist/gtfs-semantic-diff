# GTFS service_id の類型学：運行日エンコーディングの実態と、表現に依らない分類の方法

GTFS で「この便はいつ走るか」を表すのは calendar.txt と calendar_dates.txt、
そしてそれらを trips.txt に結びつける service_id である。仕様としては
単純だが、実際のフィードを数百件読むと、**同じ運行実態が驚くほど多様な
書き方でエンコードされている**ことがわかる。たとえば「毎週水曜だけ走る便」は、
calendar の曜日フラグで書くこともできるし、calendar_dates に水曜の日付を
44個列挙して書くこともできる。データとしては別物だが、利用者にとっては
どちらも同じ「水曜ダイヤ」である。

筆者らは、新旧2世代の GTFS を比較して「路線廃止・減便・乗り場変更」の
ような意味的な差分を抽出するツール（gtfs-semantic-diff）を開発する過程で、
この多様性に正面からぶつかった。差分を意味として言うためには、その前提と
して「この service は何曜日のダイヤなのか」を正しく言えなければならない
からである。本稿は、国内596フィードと海外8フィード（オランダ国家統合・
スイス国家統合・モントリオール STM・ボストン MBTA・ローマ・ピッツバーグ
PRT・ポートランド TriMet・ロサンゼルス LA Metro）の実データ調査から得た
**service_id の付け方の類型カタログ**と、それらを**特定のフィードに
依存しない決定的なルール**で分類する方法を解説する。

想定読者は、GTFS を扱うプログラムを書く開発者である。時刻表表示・運行日
検索・統計・データ検証など、「平日なら」「土曜なら」のように**運行日の
分類に応じてシステムの振る舞いを変えたい**場面は多い。そのとき素朴な
実装がどの類型のデータで壊れるか、どう正規化すれば表現の多様性を吸収
できるか、という知見は、ツールの種類を問わず再利用できるはずである。

## 1. 何が難しいのか：仕様の自由度と「表現≠意味」

GTFS の運行日モデルを確認しておく。

- **calendar.txt**: service_id ごとに、曜日フラグ7個（月〜日）と有効期間
  （start_date〜end_date）を持つ。「この期間の毎週この曜日に走る」という
  宣言である。ファイル自体が任意（無くてもよい）。
- **calendar_dates.txt**: service_id ごとの日付単位の例外。
  exception_type=1 でその日を運行日に**追加**、2 で**削除**。
  calendar なしでこのファイルだけを使うこともできる。

この2つは自由に組み合わせられるため、同じ意味に対して複数の表現が成立
する。冒頭の「毎週水曜」の例がまさにそれで、しかも後述のとおり実在の
フィードは本当に両方の書き方をしている。

したがって、**service_id の値やファイル構成そのものに意味を求めては
いけない**。プログラムが拠り所にできるのは、両ファイルを合成して得られる
**実効運行日集合** — その service が結局どの日に走るのかの集合 — だけで
ある：

```
実効運行日集合 = (有効期間 × 曜日フラグ該当日) − 削除日 + 追加日
                 （フィード全体の有効期間が分かる場合はそれでクリップ）
```

本稿で述べる分類はすべて、この集合（と、フラグという「書き手の宣言」）
から決定的に導出される。国民の祝日カレンダーのような外部知識は参照
しない。祝日情報は国・地域・年に依存し、それを参照した瞬間に手法が
特定の地域向けになってしまうからである。

## 2. 分類の語彙：何に分類したいのか

類型の話に入る前に、分類の**出力側**の語彙を定義しておく。本稿（および
筆者らのツール）では、service を次の8区分のいずれかに分類する。

| 区分 | 意味 |
|---|---|
| 平日 | 月〜金の毎週運行 |
| 土曜 | 土曜のみの毎週運行 |
| 日祝 | 日曜のみの毎週運行（日本では祝日を日曜ダイヤで運行する事業者が多く、実質「日曜・祝日」を意味することが多い） |
| 土日 | 土曜と日曜の毎週運行 |
| 毎日 | 全曜日の運行 |
| 曜日指定 | 上記に当てはまらない曜日の組の毎週運行（月・水・金曜のみ、など） |
| 特定日 | 曜日の規則では説明できず、個々の日付でしか言えない運行。年末年始ダイヤ・イベント臨時便・お盆の代替ダイヤなど。本稿ではこの意味で「特定日」という語を使う |
| 運行日なし | service は定義されているが実効運行日が1日もない（休止中の枠、期限切れの残骸など） |

「曜日指定」について補足する。平日・土曜・日祝・土日・毎日という固定の
区分だけでは、コミュニティバスに多い「月・水・金曜のみ」「火・木曜のみ」
のような運行を表せない。かといってこれらを特定日に落とすと、完全に
規則的な週次運行が「日付でしか言えない運行」と同じ扱いになってしまう。

そこで筆者らのツールでは、固定区分に収まらない曜日の組を、
**`dow_1010100` のような文字列**で表している。`dow` は day of week
（曜日）の略、続く7桁は月曜から日曜の順のビット列で、`dow_1010100` なら
「月・水・金曜」である。つまり列挙型（enum）の値を増やすのではなく、
**「どの曜日に走るか」の集合そのものを値にした開放的なラベル**である。
この設計にした理由は、曜日の組は2^7 通りあり得て列挙し切れないことと、
値だけから曜日集合を機械的に復元できれば、表示名の生成（「月・水・金曜」）
や包含関係の判定（月・水・金 ⊂ 平日）を、追加の対応表なしに下流の
どの処理でも行えることである。

この語彙を固定の列挙型にせず開放的にしたことの効果は実測できる。
「平日/土/日に当てはまらないものは全部特定日」という設計で国内43フィードを
分類した場合、特定日に落ちる便数のうち **83% は、実はこうした規則的な
曜日指定運行**だった。特定日という区分は本来「本当に日付でしか言えない
もの」のための最後の受け皿であって、そこが最大勢力になるのは分類の失敗
である。

## 3. 類型カタログ：service_id はこう書かれている

以下は実データで観測した10類型である。それぞれに、データの見た目・実例・
**素朴な実装が踏む罠**を添える。ここでいう素朴な実装とは、「calendar の
フラグを見て平日/土曜/日祝を判定し、calendar_dates は例外扱いで無視するか、
まとめて臨時扱いにする」程度の、多くのツールが最初に書くコードを指す。

### 類型A：教科書型（フラグ＋祝日例外）

```
calendar:        平日 1111100 / 土日祝 0000011
calendar_dates:  祝日に「平日」を type=2 で運休、「土日祝」を type=1 で運行
```

日本の事業者系フィードの多数派。仕様の意図どおりの素直な使い方である。
祝日を日曜側に振り替える例外が付くのが日本的な特徴で、これが前節の
「日祝」区分の由来でもある。この類型で困ることは少ないが、祝日例外の
1行1行を「ダイヤ変更」と誤検出しないためには、新旧データの例外日を
突き合わせる処理が必要になる。

### 類型B：曜日フラグによる曜日指定運行

```
calendar: 月水金便 1010100 / 木曜便 0001000
```

コミュニティバスの通学日運行・診療日運行などに多い。データとしては
完全に仕様どおりで、罠はデータ側ではなく**受け手の語彙**にある。
分類の出力が「平日/土/日/その他」の4値しかないシステムでは、月水金便も
木曜便も「その他」に落ち、互いに区別されないまま合算される。前節の
`dow_` ラベルはこの類型への対処である。

### 類型C：全列挙型（calendar_dates だけで書く）

```
calendar: なし（またはこの service の行がない）
calendar_dates: 運行するすべての日を type=1 で列挙
                （1 service あたり年間200〜300行になる）
```

日本では特定の作成ツール由来のフィードに多く、海外では**オランダの
国家統合フィード（OVapi）が全 5,062 service をこの型で書いている**。
ローマ市のフィードも同様である。つまりこれは例外的な書き方ではなく、
世界的にはひとつの主流である。

罠：「calendar_dates に列挙された運行日＝臨時・特定日」という思い込みで
実装すると、**フィード全体が特定日運行に分類され、曜日の概念が消える**。
列挙の中身は、次の類型Dのようにたいてい規則的である。

### 類型D：列挙による曜日指定運行（類型Cの中の規則性）

```
service_id「特別ダイヤ１」: 毎週水曜の日付を44個列挙（根室交通）
service_id「月水」「火木金」: 名前の通りの曜日の日付を列挙（射水市）
service_id「月・木」: 同上（黒部市）
```

作成者は曜日運行のつもりで、**service_id の名前にまでそう書いている**のに、
データ上は日付の羅列になっている類型である。類型B（フラグによる曜日指定）と
意味は同じで、表現だけが違う。

この類型の罠は少し込み入っているので、順を追って説明する。日付列挙型の
service を分類しようとするとき、素朴に思いつくのは「列挙された日付の
曜日分布を見る」方法である。列挙日の大半が月〜金なら平日ダイヤ、大半が
土曜なら土曜ダイヤだろう、という多数決である。実際、筆者らのツールも
当初この方法だった。

ところが「毎週水曜」の service にこの多数決を適用すると、水曜は月〜金の
一員なので、列挙日の100%が平日に該当し、**「平日」と分類されてしまう**。
service のデータそのものが他と混ざるわけではない。問題は**分類名**である。
同じフィードには本来の平日ダイヤ（月火木金に走り、例外指定で水曜を運休
している）が別 service として存在するから、「平日」という同じ分類名の下に、
**運行日が1日も重ならない2つのダイヤが並ぶ**ことになる。平日ダイヤを
表示・集計しようとする処理は、この2つを「平日①」「平日②」のように
機械的な番号で区別するしかなくなり、見出しから意味が読めなくなる。
実際、筆者らのツールでは根室交通の路線ページの平日タブが4つに分裂する
という形でこの問題が顕在化した。正しい姿は「平日（月火木金）」と「水曜」
という**別の分類名**である。

対処は §4 で述べる**曜日プロファイル検出**である。要件をひとことで言えば、
フラグで書かれた類型Bと列挙で書かれた類型Dが**同じ分類名に正規化される**
こと — 表現の違いを意味の違いにしないこと — である。

### 類型E：特定日運行を calendar の曜日フラグで定義する型

```
calendar: ある曜日のフラグを立て、期間は通年
calendar_dates: その曜日の通常日をほぼ全部 type=2 で削除し、
                狙った特定日（祝日など）だけを残す
```

ピッツバーグ PRT で観測した、米国のフィードに見られる流儀である。
「祝日は日曜ダイヤ相当で運行」を実現するために、日曜ダイヤのコピーに
曜日フラグを立てて、フラグ該当日をほぼ全部削除し、祝日だけを残す。
観測例ではたまたま土曜フラグが使われていたが、それは本質ではない —
**特定の数日だけ走らせたい service を、日付の追加指定ではなく
「曜日フラグ＋大量削除」で定義している**ことがこの類型の正体であり、
フラグの曜日は何であってもあり得る。

罠：フラグだけを信じて分類すると、実効運行日が年に数日しかない service が
「土曜ダイヤ」（あるいは平日ダイヤ等）として通常ダイヤの隣に並び、
**その曜日の便数が二重計上される**。

対処は**密度**を見ることである。実効運行日数 ÷（期間内のフラグ該当日数）を
計算すると、この類型は極端に低い値になる（PRT の実測で 0.06）。一方、
後述の類型F（期間分割）のような「期間は短いが正規のダイヤ」は 0.9〜1.0 に
なる。日数の絶対値ではなく密度で切ることで、「フラグは宣言として尊重するが、
宣言と実態が大きく乖離していたら実態を採る」という判定ができる。

### 類型F：期間分割（シーズン・四半期・学期ごとに別 service）

```
25M-…（2025年春ダイヤの service 群）: 有効期間 3月末〜6月
25U-…（2025年夏ダイヤの service 群）: 有効期間 6月末〜8月
```

モントリオール STM やスイスの国家統合フィードで観測。**1つのフィードの
中に、計画として複数の期間のダイヤが同居している**類型である。同じ
「土曜ダイヤ」に相当する service が、春ダイヤと夏ダイヤで別 service に
なる。平日も日祝も同様である。

罠：期間の存在を無視して分類名で集計すると、**どの分類の便数も
「同居している期間の数」倍になる**。「今日走る便」を出すだけのアプリは
日付フィルタで自然に回避できるが、時刻表の比較・統計・データ検証のような
**期間をまたいで集計する**処理は必ず踏む。

なおこの類型は、次の類型G（世代同梱）と機械的な症状がよく似ているため、
違いを明確にしておく。類型Fは**1つの版の中の恒常的な期間構成**である —
春・夏・秋・冬のダイヤはすべて「現行の計画」であり、境界は季節の変わり目
として何度も現れる。対して類型Gは**改正前の版と改正後の版という、
本来別々の2つのデータが移行期に一時的に同居している**状態で、境界は
「改正日」ただ1つ、しばらくすると旧世代を含まない版が再配布されて解消
する。対処も異なり、Fは「分類名の中を期間で分解し、対応する期間同士を
比べる」、Gは「改正日を検出し、旧データの改正前部分と新データの改正後
部分を比べる」ことになる。

### 類型G：世代同梱（改正前後のデータの同居）

```
旧ダイヤの service 群（〜改正前日で終了）
＋新ダイヤの service 群（改正日から開始）が1つの zip に同梱
```

国内のバスロケーションシステム連動のフィードで、ダイヤ改正のたびに
約1週間ほど流通する形である。筆者らは三重交通桑名地区で、改正前のみ →
改正前後の同梱 → 改正後のみ、という3段階の遷移として観測した。

罠：同梱期間のフィードを素朴に前後の版と比較すると、旧版には新世代が
なく新版には旧世代の一部がないため、**全便が半減・倍増したように見える**。
また同梱版どうしを比較すると「変化なし」に見える（どちらにも同じ両世代が
入っているため）。実際に起きたことは「改正」なのだから、旧世代の
改正前ダイヤと新世代の改正後ダイヤを比べるのが正しい。

対処：すべての分類名について一斉に「ある日を境に、旧側のダイヤが終わり
新側のダイヤが始まる」という単調な交代が観察できた場合に限り、その日を
改正日と認定して比較範囲を切り替える。1つでも反例の分類があれば認定
しない、という保守的な判定にしている。

### 類型H：全期間 service と期間分割 service の混在

```
GLOBAUX（全域共通の service）: シーズン全期間をカバー
H50〜H62（営業所別の service）: シーズン内で前半版と後半版に分割
JV00A（特異日版）: 特定の1日だけ全営業所のダイヤを丸ごと差し替え
```

STM で観測した、現時点で筆者らも完全には解けていない類型である。
営業所ごとの service が期間分割されている（類型F）だけでなく、
**シーズン全期間をカバーする共通 service が併走している**。

これが何を壊すかというと、「実効運行日が1日でも重なる service 同士を
同じグループとみなす」という推移的なグルーピングである。期間前半の
service と後半の service は日付を共有しないので本来別グループになる
はずだが、**全期間 service が前半とも後半とも日付を共有している**ため、
それを経由して連鎖的に全部が1つのグループにつながってしまう。

実測してみると、この類型の service 間の日付集合の関係は「完全一致
（営業所どうしの並走）」「包含（全期間 service が分割 service を含む）」
「互いに素（前半と後半）」がほぼすべてで、真に曖昧な部分重なりは
特異日版がらみの8組しかなかった。つまり**データは構造的には分解可能**で
あり、単純な推移的グルーピングではなく、日付集合の一致・包含・排他の
関係を直接見る方法に置き換えるべき類型である（本稿執筆時点で設計中）。

### 類型I：季節限定・期間内は毎日

```
上高地線「上高地通常」: 4〜11月の全日を列挙（213日、全曜日を完全カバー）
```

観光路線に多い。日付の列挙（類型C）で書かれることが多く、素朴な実装では
「特定日運行213日」という、正しいが意味の薄い分類になる。実態は
「季節限定だが、季節の中では毎日」であり、「毎日（4/17〜11/15）」と
言えたほうがはるかに読みやすい。

ただし「毎日」への分類は慎重さが要る。実データには「4日のうち3日走る」
ような歯抜けの準毎日運行も存在し（全曜日をカバーするが被覆率は0.75）、
これを「毎日」と断定すると嘘になる。利用者は「毎日＝いつ行っても走って
いる」と読むからである。筆者らは、毎日と断定する場合に限り全曜日の
被覆率に高い閾値（0.9）を課している。「月・水・金曜」のような分類は
多少の歯抜け（祝日運休など）があっても意味が保たれるが、「毎日」は
歯抜けに弱い — **分類名が主張する内容の強さに応じて、要求する証拠の
量を変える**という一般則である。

### 類型J：データ整備の癖（ミスと、未来の精度低下）

最後の類型は、エンコーディングの選択ではなく**データ品質のパターン**である。

- **期間初日の削除漏れ**。年末ダイヤと正月ダイヤを日付列挙で書き分けた
  ときに、双方が有効期間の初日（たとえば 2/28）を削除し忘れ、実効運行日
  として両方に残ってしまう例（立川市で観測。STM にも同型のシーズン初日の
  残骸がある）。データの字面は「2/28 には年末ダイヤと正月ダイヤの両方が
  走る」と主張していることになる。
- **未来の未整備**。毎週水曜の差し替え日付が、データ公開時点から半年分
  しか列挙されておらず、それ以降の「平日」service は水曜を含んだまま、
  という例（根室交通で観測）。これはミスというより、**改訂版が出る前提の
  暫定**である。ダイヤデータは直近が高精度で、未来へ行くほど精度が下がる。
  したがって有効期間の「開始日のばらつき」には意味があるが、「終了日の
  ばらつき」を深刻に受け取りすぎるべきではない。

この類型への対処の原則は、**データのミスを推測して解釈ルールを曲げない**
ことだと考えている。「これは削除し忘れだろう」とプログラムが忖度し始めると、
正しいデータの解釈まで歪む。代わりに、断定できなくなった箇所では**出力の
断定を弱める** — たとえば便数を「のべ28便」と表現し、「複数のダイヤが
重なる日: 2/28」と注記する — という形で、嘘をつかない範囲に踏みとどまる。

### 類型と対処の対応表

| 類型 | 実例 | 素朴な実装の症状 | 対処 |
|---|---|---|---|
| A 教科書型 | 国内多数 | （軽微） | 祝日例外の突合せ |
| B フラグの曜日指定 | コミュニティバス | 「その他」に合算 | 曜日集合をそのまま分類名に |
| C 全列挙 | OVapi 5,062件 | 全部が特定日扱い | 曜日プロファイル検出 |
| D 列挙の曜日指定 | 根室・射水・黒部 | 「平日」の分類名が衝突 | 同上 |
| E フラグで書かれた特定日 | PRT | 便数の二重計上 | 密度判定 |
| F 期間分割 | STM・スイス | 全分類で便数が期間数倍 | 分類名の中を期間で分解 |
| G 世代同梱 | 三重交通ほか | 全便半減/倍増に見える | 改正日の検出と比較範囲の切替 |
| H 全期間+分割の混在 | STM | グルーピングが全部つながる | 一致・包含・排他の直接判定（設計中） |
| I 季節毎日 | 上高地 | 「特定日213日」 | 毎日への分類（高い被覆率を要求） |
| J 整備の癖 | 立川・根室 | 偽の重複・偽の変化 | 解釈を曲げず、出力の断定を弱める |

## 4. 分類の手順（第1段）：service 1つを分類名に写す

ここからは、筆者らのツールで実際に動いている分類手順を示す。第1段は
service 1つを §2 の語彙（平日/土曜/日祝/土日/毎日/曜日指定/特定日/
運行日なし）のどれかに写す。図中の数値はいずれも設定ファイルで変更できる
閾値であり、コードへの直書きは禁止している。

```
service_id
 │
 ├─ calendar に曜日フラグ（いずれか=1）がある？
 │   │
 │   ├─ ある ──→ 実効運行日集合を計算
 │   │            ├─ 実効 0 日 ──────────────→ 運行日なし
 │   │            ├─ 密度 = 実効日数 ÷ フラグ該当日数
 │   │            │    が 0.5 未満 ──────────→ 特定日（類型E）
 │   │            └─ それ以外 → フラグの曜日集合をそのまま分類名に
 │   │                 （全平日→平日、土日→土日、全曜日→毎日、
 │   │                  その他の組→曜日指定。類型A/B）
 │   │
 │   └─ ない（類型C/D/I）──→ 追加日（exception_type=1）を集める
 │        │
 │        ├─ 運行日数 ≤ 10日 ────────────────→ 特定日
 │        │     （年末年始・お盆などの短期ダイヤ。曜日が揃っていても
 │        │      日数が少なすぎると曜日を論じる資格がない）
 │        │
 │        ├─ 曜日プロファイル検出:
 │        │     列挙日の範囲内で、曜日ごとに
 │        │       被覆率 = その曜日の運行日数 ÷ 範囲内のその曜日の総数
 │        │     を計算し、被覆率 0.6 以上の曜日を「活性」とみなす。
 │        │     ・活性曜日以外の日（祝日振替などのはみ出し）が
 │        │       全体の 10% を超えたら検出失敗
 │        │     ・全曜日が活性（=「毎日」候補）の場合だけ、さらに
 │        │       最低の被覆率が 0.9 以上であることを要求（類型I）
 │        │     成功 ──→ 活性曜日集合を、フラグと**同一の写像**で
 │        │              分類名にする（毎週水曜の列挙 → 曜日指定「水曜」。
 │        │              類型C/D が類型B と同じ分類名に正規化される）
 │        │
 │        └─ 検出失敗 → 曜日分布の多数決:
 │              80% 以上が単一区分（平日/土曜/日祝）に収まればその区分、
 │              収まらなければ特定日
 │
 └─ フラグ全0で追加日もない ──→ 運行日なし
```

設計上のポイントを3つ挙げる。

**(1) 検出 → 多数決 → 特定日、という多段のフォールバック。** 各段は
前段より弱い主張しかしない。新しい検出段を追加するときは「検出できなければ
従来と同じ挙動」を厳守する。こうすると変更の影響が「検出に成功したもの」
だけに閉じ、「検出0件のフィードでは出力が変わらない」という形で回帰
保証を書ける。

**(2) 「毎日」だけ閾値を締める非対称**（類型Iで述べたとおり）。

**(3) 短期ガードが検出より先。** 曜日プロファイルは10日程度のサンプルでは
偶然揃う（お盆の6日間はたまたま全部平日、など）。

この第1段の導入効果は定量的に測ってある。国内596フィードのうち
calendar_dates だけで書かれた service を持つのは61フィード・137 service で、
曜日プロファイル検出により分類が変わったのは18件。うち11件は service 名が
「月水」「火木金」など曜日を明記しており、**検出結果が作成者の命名と
一致した**。オランダ OVapi では 5,062 service 中約2,500件が特定日扱いから
曜日・毎日の分類に変わる。一方、フラグ運用の STM・PRT・スイス等では
変化が0件 — この検出は列挙型の表現差だけを吸収し、他を動かさない。

## 5. 分類の手順（第2段）：同じ分類名の中の構造を分解する

第1段は service 単体の分類である。しかし類型F（期間分割）と類型G
（世代同梱）は、**正しく分類しても同じ分類名の中に「日付の重ならない
別のダイヤ」が同居する**という問題であり、もう1段の構造化が要る。
筆者らはこれを次の手順で行っている。

```
同じ分類名（例: 土曜）の service 群
 │
 │ (1) 実効運行日の重なりでグループ化する
 │     ・運行日を1日も共有しない service 同士は、決して同じグループに
 │       しない（原則）。期間分割・世代同梱はここで自然に分かれる
 ▼
「土曜ダイヤその1」（4〜6月）/「土曜ダイヤその2」（6〜8月）…
 │
 │ (2) 便の内容（各便の停車順序と時刻の集まり）が完全に一致する
 │     グループ同士は、同じダイヤの日付違いとしてまとめる
 │     （例: 7/4 だけのグループと 9/7 だけのグループが同内容
 │       → 「同じ臨時ダイヤが2日走る」と読める）
 ▼
新旧世代間の対応付け（1対1）
 ・内容の完全一致（中身が同じで日付だけ変わった）
 ・日付の完全一致（同じ日付で中身が変わった）
 ・どちらでもない場合は、便同士の対応付け結果の多数決で接続
 ▼
「土曜ダイヤその1: 38便 → 38便。運行日は 5/25 から 7/4・9/7 に変更
 （内容は同一）」のような、期間まで含めた比較結果
```

ここで守っている規律は第1段と同じ形をしている。**機械が断定してよいのは
観察だけ**である。「内容が完全に一致した」「日付が完全に一致した」は
観察であり安全に言えるが、「これは祝日ダイヤだろう」「第2水曜の運行
だろう」という意味付けや規則の推定はしない。また類型J（削除漏れ）に
よってグループが不本意に融合した場合は、(1) のルールを曲げるのではなく、
出力側で「のべ◯便」という断定しない表現に切り替える。

## 7. 「特定のデータに依らない一般解」をどう守るか

分類の機構が増えるにつれ、「特定のフィードに合わせ込んでいないか」は
常に問われる。筆者らが守っている原則を明示しておく。これは開発プロセスの
話であり、同種のツールを作る読者にそのまま流用できるはずである。

1. **フィード固有の分岐をコードに置かない。** ソースコードを機械的に
   検索して、フィード名・事業者名が現れるのはコメント（この規則を
   動機づけた実例の出典メモ）だけ、という状態を保つ。すべての機構は
   「類型」に対する規則であり、**複数の独立なフィードで観測された類型**
   だけを規則化する。根室で見つけた類型Dは射水・黒部・OVapi でも成立し、
   PRT で見つけた類型Eの密度判定はスイスや STM の期間分割を誤爆しない
   ことを確認してから入れる、という進め方である。
2. **正規化の基礎をひとつにする。** すべての判定は実効運行日集合
   （＋フラグの宣言）から導く。「フラグで書かれた場合はこう、列挙なら
   こう」という表現依存の規則は置かず、表現差は正規化の段階で吸収する。
3. **閾値はすべて設定ファイルに置き、実測の分布を根拠として残す。**
4. **フォールバックは常に従来挙動。** 新しい検出が失敗したら前の規則に
   落ちる多段構成にすることで、変更の影響範囲を検出成功例に限定する。
5. **データのミスに解釈を合わせない。** ミスへの対処は出力の断定を
   弱めることで行い、解釈ルール自体は曲げない。
6. **規則を入れる前に、手元の全データへの影響を列挙する。** 新しい規則の
   候補ができたら、まず全フィードに適用して「何がどう変わるか」を列挙
   する調査スクリプトを書き、変化が意図した類型に限られることを確認して
   から実装に進む。

機構の数は増えたが、それは**規則の数**が増えたのであって、規則の**性格**が
変わったのではない。各規則は独立に無効化でき、適用条件が観察可能で、
失敗時の挙動が定義されている。むしろ危険なのは、類型を知らずに1つの
規則（たとえば曜日分布の多数決）で全類型を捌こうとすることで、それは
「単純」なのではなく「未分化」なのだと考えている。

## 8. 開発者への示唆（持ち帰り用の要点）

- **service_id の値やファイル構成に意味を求めない。実効運行日集合に
  正規化してから、すべてを始める。**
- **運行日の分類を閉じた列挙型にしない。** 「どの曜日に走るか」の集合を
  値としてそのまま持てる表現（例: 月→日の7ビット文字列）にしておくと、
  表示名の生成も包含判定も下流で完結する。
- **calendar_dates に列挙された日付を、それだけで臨時・特定日と
  みなさない。** まず曜日の規則性を検出する。ただし短期間の service を
  先に除外し、「毎日」の断定には高い被覆率を要求する。
- **フラグは宣言、実効日は実態。両方を見る。** 宣言と実態の乖離
  （フラグはあるのに実効日が数日）は密度で捕まえられる。
- **「運行日が1日でも重なれば同じグループ」という推移的なグルーピングは、
  全期間をカバーする service が混ざると崩壊する。** グループ化の前に、
  service 間の日付集合の関係（一致・包含・部分重なり・排他）の分布を
  測っておくと、規則がどう壊れるかを予測できる。
- **未来の日付ほど信頼しない。** データ終端付近の差異に強い意味を
  与えない。有効期間の開始日の違いには意味があるが、終了日の違いは
  しばしば整備の都合にすぎない。
- **分類規則を追加するときは、影響調査 → 保守的な閾値 → フォールバック →
  回帰確認の順で。** 分類器はシステムの土台であり、その変更は全出力に
  波及する。

## 9. 未解決の類型と今後

- **類型H（全期間 service と分割 service の混在）**: 推移的グルーピングを
  「日付集合の一致・包含・排他の直接判定」に置き換える設計を検討中。
  完全一致（並走）は束ね、包含（全期間 service）は両側に重ねて数え、
  排他（前半と後半）だけを別のダイヤとする方向である。
- **有効期間が重ならない2世代の比較**: 期間分割された旧データの一部
  （たとえば夏ダイヤ）に、新データ側の対応する期間が存在しない場合、
  それを「廃止」と区別して「比較対象期間なし」と言う必要がある。
- **祝日の意味論**: 外部の祝日カレンダーを参照しない方針は維持した上で、
  「祝日は日曜ダイヤと同内容」という**観察**（実効日と便内容の一致）だけ
  からどこまで言えるかを見極めるのが次の課題である。
