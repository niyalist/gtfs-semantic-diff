# GTFS service_id の類型学：運行日エンコーディングの実態と、表現に依らない分類パイプライン

GTFS で「この便はいつ走るか」を表すのは calendar.txt と calendar_dates.txt、
そしてそれらを trips に結びつける service_id である。仕様としては単純だが、
実際のフィードを数百件読むと、**同じ運行実態が驚くほど多様な書き方で
エンコードされている**ことがわかる。「毎週水曜だけ走る便」は、曜日フラグで
書くこともできるし、水曜の日付を44個列挙して書くこともできる。データとしては
別物だが、利用者にとっては同じ「水曜ダイヤ」である。

gtfs-semantic-diff（新旧2世代の GTFS から「路線廃止・減便・乗り場変更」の
ような意味的差分を抽出するツール）の開発では、この多様性が最大の難所の
ひとつだった。本稿は、国内596フィード＋海外8フィード（オランダ国家統合・
スイス国家統合・モントリオール STM・ボストン MBTA・ローマ・ピッツバーグ PRT・
ポートランド TriMet・ロサンゼルス LA Metro）の実データ調査から得た
**service_id の付け方の類型カタログ**と、それを**特定のデータに依らない
決定的ルール**で分類するパイプラインを解説する。

想定読者は GTFS を扱うプログラムを書く開発者である。「平日なら」「土曜なら」
のように**分類に応じてシステムの振る舞いを変えたい**とき、素朴な実装が
どの類型で壊れるか、どう正規化すれば表現の多様性を吸収できるか、という
知見はツールの種類を問わず再利用できるはずだ。

## 1. 何が難しいのか：仕様の自由度と「表現≠意味」

GTFS の運行日モデルはこうなっている。

- **calendar.txt**: service_id ごとに曜日フラグ7個（月〜日）と有効期間
  （start_date〜end_date）。ファイル自体が任意。
- **calendar_dates.txt**: service_id ごとの例外。exception_type=1 で
  その日を運行に**追加**、2 で**削除**。calendar なしで単独使用も可。

この2つの自由な組み合わせにより、同じ意味に対して複数の表現が成立する。
逆に言えば、**service_id の生の値やファイル構成に意味を求めてはいけない**。
プログラムが拠り所にできるのは、両ファイルを合成して得られる
**実効運行日集合**だけである：

```
実効運行日集合 = (有効期間 × 曜日フラグ該当日) − 削除日 + 追加日
                 （フィードの有効期間でクリップ）
```

本稿で述べるすべての分類は、この集合（と、フラグという「書き手の宣言」）
から決定的に導出される。祝日カレンダー等の外部知識は参照しない —
祝日情報は国・年に依存し、参照した瞬間に「一般解」でなくなるからである。

## 2. 類型カタログ：service_id はこう書かれている

以下は実データで観測した10類型である。各類型に、データの見た目・実例・
**素朴な実装が踏む罠**を添える。ここでいう素朴な実装とは「calendar の
フラグを見て平日/土日を判定し、calendar_dates は無視するか特定日扱いする」
程度の、多くのツールが最初に書くコードを指す。

### 類型A：教科書型（フラグ＋祝日例外）

```
calendar:        平日 1111100 / 土日祝 0000011
calendar_dates:  祝日に 平日を type=2、土日祝を type=1
```

日本の事業者系フィードの多数派。祝日を「日曜側に振り替える」例外が
付くのが日本的特徴（祝日ダイヤ＝日祝ダイヤの一体運用）。
罠は少ないが、祝日例外を「ダイヤ変更」と誤検出しないためには
例外日の突合せが要る。

### 類型B：曜日フラグ型（週の部分集合）

```
calendar: 月水金便 1010100 / 木曜便 0001000
```

コミュニティバスの通学日運行・診療日運行等。国内43フィードの実測では、
従来「特定日」に分類されていた便数の **83% が実はこの型の規則的な
週次運行**だった。罠：「平日/土/日」の3区分しか持たないシステムでは
これらが全部「その他」に落ち、月水金便と木曜便が同じ箱で合算される。

対処：曜日集合をそのまま型にする。gtfs-semantic-diff では
`dow_1010100`（月→日の7ビット）という**値から曜日集合を復元できる
ラベル**を第一級の型にした。enum に閉じないことで、消費側（表示・
包含判定）が追加のメタデータなしで「月水金 ⊂ 平日」を計算できる。

### 類型C：全列挙型（calendar_dates only）

```
calendar: なし（または対象 service の行なし）
calendar_dates: 運行する日を全部 type=1 で列挙（年間200〜300行/串）
```

日本では「その筋屋」等の作成ツール系フィードに多く、海外では
**オランダ OVapi が全 5,062 service をこの型で書く**。ローマも同様。
罠：列挙＝「特定日」と解釈すると、**フィード全体が特定日運行**になり、
曜日の概念が消える。列挙の中身はたいてい規則的である（次の類型D）。

### 類型D：列挙による週次運行（類型Cの中の規則）

```
service_id「特別ダイヤ１」: 毎週水曜の日付を44個列挙（根室交通）
service_id「月水」「火木金」: 名前の通りの曜日を列挙（射水市）
service_id「月・木」: 同上（黒部市）
```

**作成者は曜日運行のつもりで、名前にまでそう書いている**のに、
データ上は日付の羅列である。ここに本稿の核心的な罠がある：
曜日分布の「平日/土/日」3ビン多数決で分類すると、毎週水曜は水曜が
100%平日なので **weekday と判定される**。すると同じフィードの
「平日」service と同じ箱に入り、しかも運行日は互いに素（平日 service は
例外で水曜を削除している）なので、**「平日」の中に日付の重ならない
複数のダイヤが同居**する。gtfs-semantic-diff ではこれが「平日タブが
①〜④に分裂する」表示として顕在化した（§5）。

対処が §4 の**曜日プロファイル検出**である。フラグで書かれた類型Bと
列挙で書かれた類型Dが**同じラベルに正規化される**こと — 表現の違いを
意味の違いにしないこと — が要件になる。

### 類型E：祝日専用 service（米国流の引き算）

```
calendar: 土曜フラグ 0000010、期間は通年
calendar_dates: 通常の土曜を全部 type=2 で削除、独立記念日だけ残す
```

ピッツバーグ PRT で観測。「祝日は日曜ダイヤで運行」を、日曜ダイヤの
コピーに土曜フラグを付けて実現する流儀。実効運行日は年に1〜数日なのに、
フラグだけ見ると土曜ダイヤに見える。罠：土曜の便数が2倍になる。

対処：**密度**で判定する。実効運行日 ÷（期間×フラグ該当日）が閾値
（0.5、実測では祝日専用 0.06 vs 正規ダイヤ 0.9〜1.0）未満なら、
フラグではなく実態（特定日）を採る。日数でなく密度を使うのは、
期間分割された正規ダイヤ（次の類型F）を誤って特定日に落とさないため。

### 類型F：期間分割（シーズン・四半期・学期）

```
25M-…（2025春の各営業所 service）: 3月末〜6月
25U-…（2025夏）: 6月末〜8月
```

モントリオール STM、スイス統合フィード等。同じ「土曜ダイヤ」が
シーズンごとに別 service になる。罠：ラベルで合算すると土曜の便数が
シーズン数倍になる。「今日の便」を出すだけのアプリでは日付フィルタで
自然に回避されるが、**時刻表比較・統計・差分**のような「期間をまたいで
集計する」処理は必ず踏む。

対処：ラベルの中を**実効運行日の重なりで分解**する（§5 の運行日世界）。

### 類型G：世代同梱（改正前後の同居）

```
旧ダイヤの service 群（〜改正前日）+ 新ダイヤの service 群（改正日〜）
を1つの zip に同梱
```

国内のバスロケ連動システム（bus-vision 系）で改正のたびに約1週間流通する。
三重交通桑名では A → A+B → B という3世代の遷移として観測された。
罠：同梱フィードを素朴に前後比較すると**全便半減/倍増**に見える。

対処：全ラベルで一斉に「旧末尾世界が新側に持ち越され、新側に新世界が
現れる」単調交代を検出したら、旧データの改正前 × 新データの改正後を
比較する（切替日の明示）。

### 類型H：傘＋差し替え（未解決の最難関）

```
GLOBAUX（全域 service）: シーズン全期間をカバー
H50〜H62（営業所別 service）: シーズン内で -70- 版 → -80- 版に差し替え
JV00A（特異日版）: 3/7 の1日だけ全営業所を全面差し替え
```

STM で観測。営業所別・改定版別・特異日差し替えが**傘 service を橋として
互いに日付を共有**するため、「1日でも共有したら同一視」型のグルーピングは
全部が1つに融着する。実測では日付集合の対関係は equal（並走）・nested（傘）・
disjoint（差し替え）がほぼ全てで、本質的に曖昧な partial は特異日の8組
のみ — つまり**データは構造的に分解可能**であり、連結成分より細かい
「日付集合の同値類＋包含」で見るべき類型である（本稿執筆時点で設計中）。

### 類型I：季節毎日（期間限定・期間内は毎日）

```
上高地線「上高地通常」: 4〜11月の毎日を列挙（213日、全曜日被覆 1.0）
```

観光路線に多い。罠：列挙＝特定日扱いだと「特定日213日」という
意味の薄い表示になる。対処：曜日プロファイル検出で daily に。ただし
**全曜日被覆が高い場合だけ**（後述の保守的閾値）。「4日に3日走る」ような
歯抜けの準毎日（被覆0.75）まで「毎日」と断定すると嘘になる。

### 類型J：整備の癖（ミスと未来の減衰）

これはエンコーディングの類型ではなく、**データ品質の類型**である。

- **期間初日の削除漏れ**: 年末ダイヤと正月ダイヤの両方が、有効期間初日
  （2/28）を calendar_dates で削除し忘れ、実効日に共有日 2/28 が残る
  （立川市。STM にも同型のシーズン初日残りがある）。機械的には
  「2/28 に両ダイヤが走る」というデータの主張になる。
- **未来尾部の未整備**: 毎週水曜の差し替え列挙が公開から半年分しかなく、
  それ以降の「平日」は水曜を含んだまま（根室交通）。改訂版が出る前提の
  暫定であり、**ダイヤデータは直近が高精度・未来ほど低精度**という
  非対称がある。有効期間の「開始のばらつき」は意味を持つが、
  「終了のばらつき」は真剣に扱いすぎない方がよい。

対処の原則：**データのミスに解釈を合わせない**。ミスを推測して規則を
曲げると、正しいデータの解釈まで歪む。代わりに、断定できない箇所は
表示の側で断定を弱める（「のべ28便」＋「複数ダイヤが重なる日: 2/28」の
ような注記）。

### 類型と対処の対応表

| 類型 | 実例 | 素朴実装の症状 | 対処機構 |
|---|---|---|---|
| A 教科書型 | 国内多数 | （軽微） | 祝日例外の突合 |
| B 曜日フラグ | コミュバス | 「その他」に合算 | dow_XXXXXXX 一級化 |
| C 全列挙 | OVapi 5,062件 | 全部が特定日 | 曜日プロファイル検出 |
| D 列挙の週次 | 根室・射水・黒部 | 平日に混入→分裂 | 同上 |
| E 祝日専用 | PRT | 土曜が2倍 | 密度判定 |
| F 期間分割 | STM・swiss | ラベル合算で倍増 | 運行日世界 |
| G 世代同梱 | bus-vision | 全便半減/倍増 | 切替検出 |
| H 傘＋差し替え | STM | 全部が融着 | （設計中） |

## 3. 分類パイプライン（第1段）：service_id → day_type ラベル

第1段は service 1つを day_type ラベル（weekday / saturday /
sunday_holiday / weekend / daily / dow_XXXXXXX / irregular / inactive）に
写す。全体は次のフローになる。閾値（括弧内）はすべて設定ファイルの値で、
コード内リテラルは禁止している。

```
service_id
 │
 ├─ calendar に曜日フラグ (いずれか=1) がある？
 │   │
 │   ├─ ある ──→ 実効運行日集合を計算
 │   │            ├─ 実効 0 日 ────────────────→ inactive（休止中の枠）
 │   │            ├─ 密度 = 実効日/フラグ該当日
 │   │            │    < min_flag_day_ratio (0.5) → irregular（類型E: 祝日専用）
 │   │            └─ それ以外 → フラグ写像 ─────→ weekday / saturday /
 │   │                 （月金のみ等はそのまま）     sunday_holiday / weekend /
 │   │                                             daily / dow_XXXXXXX（類型B）
 │   │
 │   └─ ない（類型C/D/I）──→ 追加日 (exception_type=1) を集める
 │        ├─ ≤ short_service_max_days (10日) ──→ irregular
 │        │        （年末年始・お盆等の短期ダイヤ。曜日が揃っていても特定日）
 │        ├─ 曜日プロファイル検出:
 │        │     span 内の各曜日の出現率 cov[曜] を計算し
 │        │     cov ≥ dow_on (0.6) の曜日を「活性」とする
 │        │     ・活性曜日外の日の比率 > dow_stray_max (0.1) → 検出失敗
 │        │     ・全曜日が活性（=daily 候補）のときだけ、さらに
 │        │       min(cov) ≥ dow_daily_min_cov (0.9) を要求（保守的閾値）
 │        │     成功 ──→ 活性曜日集合をフラグと同一の写像へ
 │        │              （毎週水曜の列挙 → dow_0010000。類型D/I の解決）
 │        └─ 検出失敗 → 曜日分布の3ビン多数決
 │              ≥ calendar_dates_majority (0.8) → weekday/saturday/sunday_holiday
 │              届かない ────────────────────→ irregular
 │
 └─ フラグ全0・追加日もなし ──→ inactive
```

設計上のポイントを3つ挙げる。

**(1) 検出→多数決→irregular の多段フォールバック。** 各段は前段より
弱い主張しかしない。新しい検出段を足すときは「検出できなければ従来
挙動」を厳守することで、変更の影響範囲が「検出できたものだけ」に閉じる
（回帰保証が「検出0件のフィードでは出力が変わらない」という形で書ける）。

**(2) daily だけ閾値を締める非対称。** 「月水金」の検出は多少の
歯抜けがあっても意味が保たれるが、「毎日」は歯抜けがあると端的に嘘に
なる（利用者は「毎日=いつ行っても走っている」と読む）。実測では
被覆1.0の季節毎日（類型I）と被覆0.75の準毎日が両方存在し、後者を
irregular に残すために daily 断定のみ最小被覆 0.9 を要求している。
**ラベルの意味論的な強さに応じて証拠の要求量を変える**という一般則である。

**(3) short ガードが先。** 曜日プロファイルは10日程度のサンプルでは
偶然揃う（お盆の6日間は全部平日、など）。日数の少ない service は
曜日を論じる資格がない、という順序にしている。

この第1段の導入効果は定量的に測ってある：国内596フィード中、
calendar_dates 専用 service を持つ61フィード137 service のうち、
曜日プロファイル検出でラベルが変わったのは18件（うち11件は service 名が
「月水」「火木金」等で**検出結果が作成者の命名と一致**）。オランダ OVapi
では 5,062 service 中約2,500件が「特定日」から曜日・毎日ラベルに変わる。
一方、フラグ運用の STM・PRT・swiss 等は影響0件 — 検出は列挙型の
表現差だけを吸収し、他を動かさない。

## 4. 分類パイプライン（第2段）：ラベルの中の構造 — 運行日世界

第1段はあくまで service 単体の分類である。類型F（期間分割）・G（世代
同梱）は、**同じラベルの中に「日付の重ならない別のダイヤ」が同居する**
問題であり、もう1段の構造化が要る。

```
同一ラベル（例: 土曜）の service 群
 │
 │  実効運行日の重なりでグルーピング
 │  ・1日も共有しない service は決して同じグループにしない（原則）
 │  ・重なる service は同一「世界」に융合
 ▼
運行日世界（土曜①: 4〜6月の12日 / 土曜②: 6〜8月の10日 …）
 │
 │  内容ダイジェスト（便の停車列×時刻の多重集合）が完全一致する
 │  世界を1つの「パターン」に束ねる
 │  （例: 7/4 だけの世界と 9/7 だけの世界が同内容 → 1パターン）
 ▼
世代間対応（旧パターン ↔ 新パターン、厳密1:1）
 ・content 信号: 内容が完全一致（日付だけ変わった）
 ・dates 信号: 日付が完全一致（内容が変わった）
 ・flow: どちらでもなければ、便対応の多数決で接続
 ▼
表示セル = タブ（土曜① 38便 → 38便 + 「旧 5/25 → 新 7/4・9/7（内容同一）」）
```

ここでも守っている規律は第1段と同じ形をしている：

- **機械が断定するのは観察だけ**。「内容が完全に一致した」「日付が完全に
  一致した」は観察であり安全に断定できる。「これは祝日ダイヤだろう」
  「第2水曜運行だろう」という意味付け・規則推定はしない。近似的な対応は
  既存の便対応アルゴリズムに委ね、新しい推測機構を足さない。
- **部分重なり（類型J の削除漏れ等）で融合した世界は、数字の断定をやめる**。
  「のべ28便」と表示し、共有日を注記する。モデルは変えず、表示の確信度
  だけを下げる。
- 世代同梱（類型G）は、全ラベル一斉の単調交代が観察できたときだけ
  切替日を認定する。1ラベルでも反例があれば発動しない。

## 5. 分類が表示をどう変えるか：実例 before → after

| フィード | 類型 | 素朴/旧実装の表示 | 現在の表示 |
|---|---|---|---|
| PRT（ピッツバーグ） | E+F | 特定日 38→76便▲（同時刻に二重） | 特定日 38→38便＋「5/25 → 7/4・9/7（内容同一）」 |
| 根室交通 落石線 | D | 平日① 1便 / ② 1便 / ③ 2便 / ④ 1→0便▼ | 平日 2便 / **水曜 3便** / 土日祝 2便 |

## 6. 「一般解」をどう守っているか

機構が増えるにつれ「特定のデータに合わせ込んでいないか」は常に問われる。
現時点での守り方を明示しておく。

1. **フィード固有の分岐がコードに存在しない。** ソースを機械的に検索して、
   フィード名・事業者名が現れるのはコメント（出典の記録）のみである。
   すべての機構は「類型」に対する規則であり、各類型は**複数の独立な
   フィードで観測されたもの**だけを採用している（根室で見つけた類型Dは
   射水・黒部・OVapi でも成立し、PRT で見つけた類型Eの密度判定は
   STM の四半期を誤爆しないことを swiss でも確認する、という進め方）。
2. **正規化の基礎はひとつ。** すべての判定は実効運行日集合（＋フラグの
   宣言）から導く。表現（フラグか列挙か）に依存した規則を置かない。
   類型Dの解決は「列挙をフラグと同じ写像に通す」ことであって、
   「根室の書き方を特別扱いする」ことではない。
3. **閾値は全部設定ファイル。** dow_on=0.6、dow_daily_min_cov=0.9 等は
   config に集約され、根拠（実測の分布）をコメントで持つ。
4. **フォールバックは常に従来挙動。** 検出に失敗したら前の規則に落ちる
   多段構成なので、「新機構の影響 = 検出に成功した集合」に限定される。
5. **ミスに解釈を合わせない。** 類型Jはデータ品質の問題であり、
   分類規則を曲げず、表示の断定を弱めることで対処する。
6. **影響は導入前に全量調査する。** 新しい規則は必ず調査スクリプト
   （手元の全フィードに規則を適用し、変化する service を列挙する）を
   先に書き、変化が意図した類型に限られることを確認してから実装する。

複雑さは増えたが、それは**規則の数**であって**規則の性格**ではない。
各規則は独立に無効化でき、適用条件が観察可能で、失敗時の挙動が定義されて
いる。むしろ危険なのは、類型を知らずに1つの規則（例：3ビン多数決）で
全類型を捌こうとすることで、それは「単純」ではなく「未分化」である。

## 7. 開発者への示唆（持ち帰り用）

- **service_id・ファイル構成に意味を求めない。実効運行日集合に正規化してから
  すべてを始める。** これだけで類型A/C/Eの差の大半が消える。
- **day_type は閉じた enum にしない。** `dow_1010100` のような「値から
  曜日集合を復元できる」表現にしておくと、包含判定（月水金⊂平日）や
  表示名生成が消費側で完結する。
- **「列挙された日付」は特定日ではない。** まず曜日プロファイルを検出せよ。
  ただし短期間ガードを先に、daily の断定には高い被覆を要求する。
- **フラグは宣言、実効日は実態。両方見る。** フラグ土曜＋実効1日（類型E）の
  ような乖離は密度で捕まえる。
- **「1日でも重なれば同じ」の連結成分は、傘 service（類型H）で崩壊する。**
  グルーピングの前に、日付集合の対関係（equal / nested / partial /
  disjoint）の分布を測っておくと、規則の壊れ方が予測できる。
- **未来の日付は信頼度が低い。** データ終端付近の差異に強い意味を
  与えない。有効期間の開始差は意味を持つが、終了差はしばしばノイズ。
- **規則を足すときは、調査スクリプト→影響列挙→保守的閾値→フォールバック
  →回帰確認の順で。** 分類器の変更はシステム全体に波及する。変化が
  「意図した類型だけ」であることを、実データの全量で確認してから出す。

## 8. 未解決の類型と今後

- **類型H（傘＋差し替え）**: 連結成分を「日付集合の同値類＋包含」に
  置き換える設計を検討中。equal（営業所並走）は束ね、nested（傘）は
  共走として合算し、disjoint（差し替え）だけを別世界にする。
